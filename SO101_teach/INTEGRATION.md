# 조립대 명령과 관제 Action

명령·준비 병행 처리의 2026-10-20 검증 근거와 실물 검증 범위는 [검증 기록](verification/RESULTS.md)에 정리했다.

Pi `10.10.142.113`, 사용자 `ubuntu`, ROS 2 Jazzy / `ROS_DOMAIN_ID=40`.
새 SSH 터미널에서는 `.bashrc`가 `/home/ubuntu/project/episode_ros_env.bash`를 불러옵니다. 이미 열려 있던 터미널은 이 파일을 한 번 다시 source합니다. 파일을 불러오는 것만으로 장비가 움직이지 않습니다.

이미 열려 있는 Pi 터미널은 `source /home/ubuntu/project/episode_ros_env.bash` 후 위 명령을 사용합니다. `work_watch`는 최근 알림 15개를 먼저 보여주며 `work_watch --tail 30`으로 개수를 바꿀 수 있습니다. 과거 완료 기록과 현재 상태는 구분해서 표시합니다. 조회 화면의 Ctrl+C는 조회만 종료하며 실행 중인 로봇 작업에는 영향을 주지 않습니다. 연결 점유·설정 오류 등 실행 준비 중의 거절도 REJECTED 이력으로 표시하며, 다른 실행 중 작업의 현재 상태는 덮어쓰지 않습니다. 티칭 앱의 수동 조작은 이 조회의 대상이 아닙니다. 서비스 상태는 시작 시 표시하고 이후 5초마다 확인해 변경될 때만 알립니다.

일반 `stop` 명령은 사용하지 않습니다. `reset` 셸 함수는 조립대 초기화 명령입니다. 터미널 자체를 초기화하려면 `/usr/bin/reset`을 사용합니다. 이전 `arm2_a/b`, `arm3_a/b`, `linear_f/r`는 새 명령을 부르는 별칭으로 남겼습니다. 임의의 리니어 세부 위치 입력은 지원하지 않습니다.

PC 화면에서도 조회할 수 있다. `bash SO101_teach/run_work_monitor.sh`는 일반 티칭 장치 연결 없이 SSH로 Pi 실행 기록과 실행기가 제공 중인 카메라 프레임을 읽는다. 관제 PC·final-action이 시작한 작업도 같은 실행 기록으로 표시한다. 일반 티칭 앱의 **상단 카메라 → 실시간 작업** 탭과 같은 화면이다. 일반 앱에서 조회 탭에 진입하면 두 팔의 유휴 티칭 연결을 `detach`하고 자동 재연결을 중지한다. 활성 동작·보정이 있으면 연결을 유지하고 완료 후 해제한다. 조회 탭을 나가는 것만으로 재연결하지 않으며 티칭 화면에서 명시적으로 연결해야 한다. 다른 PC의 사용권에는 관여하지 않는다.

조회 도우미는 별도 SSH 프로세스에서 표준 라이브러리만 사용하며 Pi 파일 설치·실행 코드 갱신·서비스 재시작을 하지 않는다. 실행기 IPC는 `inspect`, 인증된 HTTP는 `/camera` 읽기와 `/preview` 카메라 전용 구독·해제를 사용한다. 유휴 상태에는 원본 영상 미리보기를 열고 제어 요청이 오면 양보한다. 모터 사용권·설정 변경·제어 heartbeat·실행 명령은 보내지 않는다. 0.5초 간격으로 구독을 갱신하며 마지막 구독 종료 또는 4초 만료 시 자체 미리보기를 정리한다. 실행기가 사용 중인 카메라는 조회 종료로 닫지 않는다. 실물 작업 중 조회에 따른 추가 부하 측정은 아직 수행하지 않았다.

RESET·공정 완료 뒤 예약된 자동 토크 해제는 리니어 전용 명령(`BUILD_SLIDE`/`LOAD_SLIDE`)이 이어져도 유지한다. 독립 BUILD/LOAD에서도 동작하지 않는 반대쪽 팔의 기존 예약을 유지하며, 티칭 앱의 기존 연결을 빌려 실행할 때도 같은 기준을 적용한다. 작업 잠금이 있는 동안 해제를 미루고, 작업 종료 뒤 새 측정값으로 3초 정지를 확인한 후 해제한다. 원래 해제 예약이 없던 수동 HOLD나 오류 HOLD에는 새 예약을 만들지 않는다. 직접 제어권 획득이나 실제 동작할 팔의 사용권 확보, 명시적 HOLD·모터 명령은 기존처럼 해당 예약을 취소한다.

검사 실행기는 현재 판정과 같은 프레임을 최대 2 FPS의 최신 한 건으로 기록한다. 조회 화면은 실행·요청·팔 식별자가 맞는 채택 위치와 검사 근거만 표시한다. 실시간 영상에는 유효한 기준 영역을, 판정 영상에는 실제 관측 외곽과 시각을 표시하며 확대를 지원한다. 영상 표시는 검사 조건이나 모터 실행에 관여하지 않는다.

직접 실행 예:

```bash
build_a
# 또는
/home/ubuntu/OpenCV_teach/run_episode.sh build_a

# 동작 없이 파일·보정·목표 위치만 확인
/home/ubuntu/OpenCV_teach/run_episode.sh build_a --check
```

### work_watch 알림 범위

PC 상단 카메라의 **실시간 작업 → 작업 기록**도 같은 요약 규칙을 사용한다. 기본 선택은 최근 전체 기록이며 개별 실행 선택 시 해당 작업으로 좁힌다. 검사 실패 상세, 중복 원인 참조, 구간별·전체 소요시간을 함께 표시하고 원문 보기는 `work_watch --details`와 같은 형식이다. PC 화면은 최근 기록을 제한된 개수로 수신하므로 터미널의 전체 누적 이력과 보관 범위는 다르다.

- Action 서버 준비, 명령 수신·접수, 잘못된 명령·다른 팔 명령·중복 작업 거절
- CLI 준비 실패와 연결 점유, 지그 검출·확정 좌표, 리니어 이동·완료, 경로 계산
- 시작 전 검사·스텝 검사 시작/통과/실패, 스텝·단계 완료, 작업 완료·토크 해제
- 정지·재개·초기화 요청/응답/실제 완료 또는 실패, 활성 작업 없음과 확인 시간 초과
- 실행기 시작 실패·진단 출력, Action 최종 결과, 서비스 상태 변화, 이력 읽기 오류

고빈도 모터 수신값은 출력하지 않습니다. 기존 CLI 상세 이벤트는 중복 저장하지 않고, Action 접수·최종 결과는 별도 알림으로 구분합니다. 초기 거절과 제어 알림은 실행 중인 작업의 현재 상태 파일을 덮어쓰지 않습니다. 프로그램 갱신 전에 열어 둔 `work_watch`는 Ctrl+C로 조회만 종료한 뒤 다시 실행하면 서비스 변화 감시까지 적용됩니다.

## PC_BUILD_LOAD_A / PC_BUILD_LOAD_B

두 명령은 팔2 Action 경로로 접수하고 `pc_build_load_a/b`로 실행한다. 기존 `BUILD_LOAD_A/B` 레시피를 읽되 작업 ID·명령명은 구분하여 기록한다. `BUILD_DONE`은 중간 알림이며 `CHAIN_DONE`까지 성공으로 완료하지 않는다. GPU 작업별 준비·SSH 등록이 끝나기 전에는 실행 명령을 보내지 않는다. 준비 중 정지·연결 단절·Pi 실행 세대 변경은 명령을 취소한다. `--check`는 저장 레시피만 확인하고 장치나 GPU 세션을 시작하지 않는다.

현재는 저장 영상 검증 단계로 실물 실행이 비활성이다. [사용법·비교 결과](README.md#pc-협력-조립적재--2026-10-25)를 참고한다. 실제 작업 총시간과 준비 시간은 실물 비교에서 기존 작업 기록과 PC 준비 기록을 함께 대조하며, 중첩된 AI·CAD·준비 구간을 더하지 않는다.

## 실행과 비상정지

Pi 실행부는 상태 조회에 정지 세대(`stop_generation`)를 포함한다. 앱·CLI의 이동 요청은 관측한 세대를 함께 보내며, 그 사이 HOLD·토크 해제 요청이 처리되었거나 서버의 잠금·기록 저장을 기다리던 중 정지가 발생하면 이전 이동을 거절한다. 거절된 이동은 자동 재전송하지 않는다. CLI도 상태를 읽을 때 현재 제어권을 확인하므로, 팔의 사용권을 잃은 직후 새 리니어 명령을 시작할 수 없다. 이 상태 확인과 긴급정지는 경로 계산 잠금을 기다리지 않는다.

앱의 실행 기록 저장과 Pi 사용권 확인은 별도 스레드에서 처리해 화면 하트비트를 유지한다. 준비 중 취소·실패는 SSH 실행을 시작하지 않고 표시하며, 반대쪽 팔의 기존 자동 토크 해제 예약은 보존한다.

앱은 준비 완료를 처리하기 전과 SSH 작업 스레드에서도 두 팔의 통신 오류·연결 종료를 재확인한다. 준비 중 단절을 감지해 취소한 요청은 연결이 복구되어도 자동 시작하지 않는다. 새 리니어 목표는 시작 알림 기록 뒤 제어권·통신·정지·제한시간을 다시 확인한 후 전송한다. 반대쪽 팔의 제어권도 확인하며, 재개 대기를 거쳤다면 다시 검사한다.

반대쪽 팔의 상태 응답에 모터 오류·예상치 못한 연결 종료가 있거나, 실행 중인 팔의 측정이 0.5초 이상 지났거나 영점·6개 관절 정보가 불완전하면 새 리니어 목표를 보내지 않는다. 정상 OFF로 확인되어 실행 시작 전부터 종료된 동일 세션은 허용한다. 앱에서 빌린 연결도 한 번 확인한 팔로워 상태가 사라지면 실패로 처리한다.

앱은 실행마다 고유 `execution_id`를 부여하며, 수신기가 CLI 정리를 마친 뒤 보낸 `GUI_RESULT`의 ID와 결과 코드로 완료를 확정한다. 일반 출력의 `A_DONE` 같은 문자열이나 프로세스 종료 코드만으로는 성공 처리하지 않는다. 결과 코드 0은 완료, 130은 초기화 완료에 따른 원래 작업의 정지, 1은 실패다. 중간 단계 완료와 다른 실행의 결과는 전체 성공으로 인정하지 않는다. 확인된 최종 결과 뒤의 추가 출력·통신 단절은 결과를 취소로 바꾸거나 추가 HOLD를 보내지 않는다. 최종 완료 전에 접수한 사용자 취소는 계속 정지로 기록한다.

실패 결과는 필요한 HOLD 처리가 끝난 뒤 앱의 실행 소유권을 해제한다. 중복 결과나 이후의 스트림 오류로 HOLD를 반복하지 않아 다음 작업에 이전 실행의 정지 요청이 도착하지 않게 한다.

최종 결과 수신과 사용자 취소의 선후는 함께 잠금 처리한다. 결과 수신 뒤의 정지는 결과를 덮어쓰거나 HOLD를 추가하지 않으며, 명시적인 토크 해제 요청은 원래 연결·세션이 그대로일 때 마무리 후 전달한다. 준비·실행·정리에는 시작 시 확보한 연결을 사용한다. 연결 객체·접속 설정·사용권이 바뀌면 이전 요청으로 새 실행을 시작하지 않고, 이전 작업의 HOLD·토크 해제·소유권 정리가 교체된 연결에 영향을 주지 않도록 한다.

명령은 두 팔의 Pi 제어 연결과 리니어 사용권을 예약합니다. 다른 티칭 창이나 작업이 사용 중이면 거절하며 대기열에 넣지 않습니다. PC 티칭 앱을 종료하고 전원·USB·카메라·부품·지그 및 이동 경로를 준비합니다. 실제 장애물 회피는 하지 않습니다. 에피소드에 지정한 부품 검사는 아래 검사 실행 순서에 따라 수행합니다.

정상 순서: 모델 식별·가중치 사전검사 → 연결·현재 상태 확인(카메라·모델 예열 병행) → 팔 토크 준비 → 리니어 이동과 시작 안전 자세 이동 병행 → 안전 자세 도달 후 고정 지그 채택 → 보정 경로 계산과 시작 전 검사·리니어 완료 확인 병행 → 모든 준비·경로 계산 완료 → 에피소드 → 종료 안전 자세·마지막 검사 완료 → 토크 해제 요청 → 완료 반환·다음 명령 허용. 리니어와 시작 안전 자세 이동의 비간섭은 2026-10-20 사용자가 확인했습니다.

지그 위치가 확정되면 해당 좌표·스텝·보정값을 복사하여 경로를 계산합니다. 계산 중에도 카메라 검사와 상태 조회를 처리하며, 리니어 위 검사는 기존처럼 리니어 완료 이후의 영상으로 수행합니다. 모든 시작 전 검사·리니어 완료·경로 계산이 끝나야 에피소드 이동을 시작합니다. 준비 중 정지 후 재개하면 이미 채택한 지그 좌표를 유지하고 이전 경로를 폐기한 뒤 같은 좌표로 다시 계산합니다. 아직 채택을 완료하지 못한 경우에만 최초 측정을 다시 시도하며, 계산 중 설정이나 제어권이 바뀌면 결과를 거절합니다.

시작 전 검사와 중간 검사는 지정 위치만 판정하되, 부품이 어느 위치에 속하는지 구분할 때는 위치가 확정된 주변 지그·슬롯도 함께 참조합니다. 검사 목록에 직접 포함되지 않은 지그도 이미 채택됐으면 전달하며, 먼저 통과한 검사 항목을 대기 목록에서 빼더라도 해당 위치 기준은 유지합니다. 주변 위치가 갱신돼도 대상 자체의 기준이 같으면 누적 판정·통과 상태를 초기화하지 않습니다. AI는 전체 주변 기준 영역 중 겹침이 가장 큰 위치에 부품을 대응시키고 동률이면 판정을 보류합니다. CAD의 빈 영역 주변 탐색은 더 가까운 다른 지그의 기준 영역 안에 중심이 있는 부품을 해당 지그에 귀속합니다. 모든 기준 영역 바깥에 놓인 부품은 이 제외 조건에 해당하지 않습니다. 리니어는 검사 대상이 아니어도 현재 명령 상태를 조회하고, 이동 중·명령 위치 미확정 상태의 좌표는 주변 기준으로 사용하지 않습니다. ROI·안착 오차·연속 프레임 통과 조건과 검사 이력을 요구하지 않는 정책은 유지합니다.

시작 전 안착검사는 필요한 지그가 개별 채택되는 즉시 시작합니다. 다른 지그의 채택을 기다리는 동안 먼저 준비된 위치를 검사하며, 리니어 정지·목표 위치가 확인되면 같은 검사 그룹에 리니어 대상을 추가합니다. 한 프레임의 준비된 대상을 묶어 AI 추론은 한 번 수행하고, 대상별 시작 시각·연속 관측 횟수·제한시간은 독립적으로 유지합니다. 리니어 정지 확인 전 프레임이나 각 대상의 지그 채택 전 프레임은 관측 횟수에 포함하지 않습니다. 지그 위치 변경·채택 소실은 해당 대상의 임시 통과와 관측 횟수를 무효화하며, 일시정지 후 재개하면 이미 채택한 지그 좌표를 유지하면서 새 영상으로 전체 검사를 다시 시작합니다. 최종 지그 스냅샷과 일치하는 결과만 `INSPECTION_PASS`로 기록합니다.

시작 전 검사에서는 이전 결과를 먼저 반영한 뒤 필요한 새 영상 한 장만 디코딩·제출합니다. 처리 중인 영상이 있거나 모든 대상이 통과했으면 추가 추론을 시작하지 않으며, 어느 대기 대상에도 사용할 수 없는 검사 시작 전 영상은 디코딩 전에 제외합니다. 검사 가능한 대상이 생길 때 작업자를 한 번 생성하고, 지그·리니어 좌표가 갱신되면 같은 작업자에 새 좌표와 대상을 전달합니다. 변경 전 좌표로 대기·처리 중이던 영상의 결과·오류는 폐기하며, 현재 좌표의 오류는 계속 검사를 실패 처리합니다. 변경되지 않은 대상의 유효 관측 횟수는 유지합니다. 예상 좌표로 반복 준비하던 기하 투영은 실제 검사 좌표에서 계산·캐시하고, 종료 시 빈 큐 대기는 즉시 깨우되 실행 중인 네이티브 계산은 정상 종료까지 기다립니다. 최소 관측 횟수·영상 신선도·시간제한·안착 허용오차는 변경하지 않습니다. 수정 전후 저장 영상 비교와 적용 기록은 `verification/startup-work-reduction-20261025/`에 보관합니다.

같은 검사 프레임의 CAD 형상 계산과 부품 AI 추론은 병렬 실행하고, 둘 다 완료된 뒤 기존 판정 로직으로 결합합니다. 검사 작업은 확정된 지그 위치와 명령된 리니어 목표 위치의 CAD 투영·마스크를 미리 계산합니다. 리니어 목표의 사전 계산은 도착 판정이 아니며, 가상 영상은 분류·연속 관측에 사용하지 않습니다. 실제 안착 판정은 새 카메라 프레임으로 수행합니다.

`estop` 또는 Pi의 작업 실행 터미널 Ctrl+C는 로봇팔과 다음 작업 진행을 보류합니다. 이미 시작한 리니어는 원래 목표까지 계속 움직이며 재출력·타이머 초기화·재개 시간 가산을 하지 않습니다. `PAUSED`는 팔/작업 보류를 뜻하며 리니어의 물리 정지를 뜻하지 않습니다. 이미 켜진 팔 토크는 유지하고 아직 준비 전인 팔은 토크 OFF를 유지합니다. 자동으로 안전 자세로 돌아가지 않습니다. `PAUSED`가 확인된 뒤 `restart` 또는 `reset`을 사용합니다. 원래 실행 프로세스와 Action Goal은 계속 살아 있습니다.

- `restart`: 완료한 스텝은 반복하지 않습니다. 중단된 목표부터 남은 경로를 현재 유지 자세에서 재계산해 이어갑니다. 이미 확정한 보정 목표를 유지합니다. 준비 단계와 공정 중 검사 재개 모두 처음 채택한 운반용 지그·팔레트 좌표를 유지합니다. 공정 중 재검사는 같은 위치에서 새 영상의 부품·안착 상태를 확인합니다. 새 에피소드에서는 지그 위치를 새로 채택합니다. 리니어에는 재개 명령을 보내지 않습니다.
- `reset`: 남은 에피소드를 취소하고 두 팔의 저장된 종료 안전 자세 복귀를 동시에 시작합니다. 두 팔 모두 도착한 것을 확인한 뒤 토크 해제를 요청합니다. 리니어가 진행 중이면 최초 명령 완료를 기다린 뒤 팔의 안전 복귀를 수행합니다. 리니어 단독 작업도 목표 완료를 기다린 뒤 작업 취소 결과를 반환합니다. 복귀 중 `estop`과 `restart`도 적용됩니다. 안전 자세 누락·복귀 실패 시 자동으로 토크를 해제하지 않습니다.
- 통신/드라이버 오류는 사용자 비상정지와 구분하며 자동 재개하지 않습니다. 실행 프로세스가 종료되면 자동으로 이전 에피소드를 재실행하지 않습니다.

안착 불합격 등으로 실행 프로세스가 이미 종료된 경우에도 `reset`을 사용할 수 있습니다. 실패 당시의 안전 자세·팔·영점 정보를 보존하며, 명시적 reset 요청에만 안전 복귀 후 토크를 해제합니다. 일반 `reset`과 ROS의 `/arm2/data`·`/arm3/data` RESET은 모두 조립대 전체 초기화입니다. 두 팔의 저장된 안전 자세·영점을 먼저 검증하고, 두 팔의 토크 ON·정지 준비가 확인되면 arm2와 arm3에 복귀 명령을 연이어 전송합니다. 한 팔의 도착을 기다리지 않고 두 팔이 함께 복귀합니다. 진행 중인 작업을 취소한 경우 작업 중이던 팔에 먼저 명령을 전송하지만 다른 팔도 즉시 복귀를 시작합니다. 두 팔 모두 도착한 뒤 토크 해제를 요청하고 RESET_DONE과 성공 결과를 반환합니다. 실제 토크 OFF는 이후 자동 해제 절차에서 확인합니다. 복귀 중에도 비상정지할 수 있으며, 다른 작업 실행 중·영점 변경·리니어 상태 미확인·안전 자세 누락이면 복귀하지 않습니다. 새 작업을 시작하면 그 팔의 이전 복귀 기록은 새 작업의 안전 자세 정보로 교체합니다. 토크가 꺼져 있어도 최신 자세 확인 후 토크를 켜고 안전 자세로 복귀한 다음 다시 토크를 해제합니다. 이미 reset을 완료한 뒤에도 저장된 복귀 정보를 다시 사용할 수 있습니다.

정상 작업은 종료 코드 0, reset으로 취소된 작업은 130, 실패는 1입니다. 제어 명령의 `…_REQUESTED`는 접수이고 실제 정지·복귀·완료는 Pi 터미널의 상세 알림으로 확인합니다. 관제의 제어 Goal 결과는 실제 정지·재개·초기화 확인 후 반환합니다.

## 리니어 상태와 시간 기준 완료

전진 100mm와 후진 1.5mm만 사용합니다. 현재 Pi의 구동 시간은 10초입니다. 동일한 목표의 `TIMED_COMPLETE` 기록이 있으면 재출력하지 않으며, 기록이 없거나 불확실하면 전체 시간으로 준비합니다.

| `position_state` | 의미 |
|---|---|
| `FORWARD` | 전진 목표 구동 시간 완료 |
| `RETRACTED` | 후진 목표 구동 시간 완료 |
| `INTERMEDIATE` | 이동 중 또는 이전 실행의 위치 미확인 |
| `UNKNOWN` | 유효한 목표/완료 정보 없음 |

리니어는 `estop`/`restart`의 영향을 받지 않습니다. 최초 명령의 완료 판정용 대기 시간만 내부적으로 유지합니다. 남은 시간 표시와 `LINEAR_PROGRESS` 카운트다운은 없으며, 이미 실행 중인 목표를 다시 보내지 않습니다. 사용권이 끊겨도 진행 중인 목표의 타이머를 동결하지 않고 완료 전 새 목표를 거절합니다. 기존 PAUSED 기록은 재시작 시 UNKNOWN으로 취급합니다.

`LINEAR_DONE:TIME_BASED`는 시간 기준 완료입니다. 실제 위치·도착 센서값이 없으므로 모든 상태에 `position_measured=false`를 유지합니다. PWM 중지가 물리 즉시 정지를 보장한다고 표시하지 않습니다.

기존 `/arm3/linear_state` Int32는 완료한 목표만 2000/1015로 발행하고, 중간/미확인 상태는 -1입니다. 새 `/arm3/linear_status` String JSON에는 `phase`, `position_state`, `target_mm`, `pause_supported=false`, `position_measured`가 있습니다. 로봇 작업 중에는 별도 리니어 명령을 거절합니다.

## 관제와 알림

동일한 `host_pkg/action/Arm` 형식을 사용합니다. 원본은 `integration/ros_ws/src/host_pkg/action/Arm.action`입니다.

```text
string command
---
bool success
string message
---
string message
```

`/arm2/data`: `BUILD_A`, `BUILD_B`, `BUILD_LOAD_A`, `BUILD_LOAD_B`, `BUILD_SLIDE`, `PREPARE_HOME`.
`/arm3/data`: `LOAD_A`, `LOAD_B`, `LOAD_SLIDE`.
Action CMD는 대문자로 통일합니다. 서버는 소문자·혼합 CMD를 접수하지 않습니다. PC `final-action`은 대문자로 전송합니다. Pi 내부 `run_episode.sh`와 셸 함수는 기존 소문자 실행 명령을 유지합니다. 두 Action 경로 모두 `EMER_STOP`, `RESTART`, `RESET`, `CLEAR_ERROR`를 접수합니다. 한 번에 하나의 조립대 작업만 실행하며, 제어 명령은 활성 작업의 종료를 기다리지 않고 처리합니다. Action cancel은 거절하고 명시적 제어 명령을 사용합니다.

`PREPARE_HOME`은 두 팔의 저장된 안전 자세와 보정값, 리니어의 완료 상태를 먼저 확인합니다. 두 팔을 차례로 안전 자세에 복귀시킨 뒤 리니어를 하차 위치 1.5mm로 이동합니다. 일반 `RESET`과 달리 팔 토크를 유지하며 `HOME_RESET_DONE`까지 완료돼야 성공합니다. `CLEAR_ERROR`는 리니어가 완료 상태일 때만 보류된 실행기를 종료하고 실행 잠금이 해제됐는지 확인합니다. 팔 복귀·작업 재개·토크 변경 명령을 보내지 않으며, 실행 중인 일반 작업에는 적용하지 않습니다.

관제는 기존 Turtle Bot 규격과 같은 성공 여부·정상/오류 표현을 유지합니다. `Arm.action` 필드는 변경하지 않습니다.

| Action 필드 | 전송 값 | 의미 |
|---|---|---|
| Feedback.message | IDLE | 정상 대기·작업 완료 |
| Feedback.message | RUNNING | 작업 처리 중 |
| Feedback.message | BUILD_DONE | `BUILD_LOAD_A/B`의 조립 단계 완료·적재 단계 진행 중 |
| Feedback.message | PAUSED | 팔/작업 보류 중 — 리니어 정지를 의미하지 않음 |
| Feedback.message | ERROR | 오류 |
| Result.success | 0 / 1 (false / true) | 요청한 명령 이행 실패 / 성공 |
| Result.message | IDLE / ERROR | 정상 수행 / 오류·미완료 |

Feedback은 상태가 바뀔 때만 전송하며 같은 상태를 반복하지 않습니다. 상세 지그·스텝·리니어 시작/완료·토크 이벤트는 관제 Action으로 전달하지 않습니다. Action Goal UUID가 작업을 구분합니다.

`BUILD_DONE`은 해당 Goal의 조립 단계가 끝났다는 중간 알림입니다. 전체 조립·적재 완료는 마지막 `IDLE` Feedback과 성공 Result로 확인합니다.

아래 상세 이벤트는 **Pi 터미널·로컬 실행 로그·기존 진단용 상태 토픽**에만 남깁니다. 관제에서 시작한 작업의 상세 출력은 `journalctl -u workcell-actions.service -f`로 볼 수 있습니다. `A_`, `B_`, `SLIDE_` 접두사를 사용합니다.

| 구간 | 이벤트 |
|---|---|
| 준비 | ACCEPTED, SAFE_POSE_STARTED, SAFE_POSE_REACHED |
| 리니어 | LINEAR_CHECK, LINEAR_READY, LINEAR_STARTED, LINEAR_CONTINUES, LINEAR_DONE:TIME_BASED |
| 지그 | JIG_DETECTION_STARTED, JIG_DETECTED, JIG_CONFIRMED, JIG_POSE |
| 계획·동작 | PLAN_STARTED, PLAN_READY, EPISODE_STARTED, STEP_DONE, STAGE_DONE, EPISODE_DONE |
| 비상정지·재개 | ESTOP_REQUESTED, PAUSED, RESUMED |
| 초기화 | RESET_STARTED, SAFE_RETURN_STARTED, SAFE_RETURN_DONE, RESET_DONE |
| 정상 마무리 | TORQUE_OFF_STARTED, TORQUE_OFF_REQUESTED, DONE (RESET은 TORQUE_OFF_CONFIRMED까지 확인) |
| 오류 | FAILED:사유, REJECTED:사유 |

조립의 STAGE_DONE은 LOWER → MIDDLE → UPPER입니다. 앱의 에피소드 조정 탭에서 지정한 완료 알림은 스텝 ID에 연결되어 이름·순서 변경에도 유지됩니다. 완료 알림 필드가 없는 기존 에피소드는 스텝 이름 규칙을 계속 사용하며, B 조립의 하단은 조정 완료 스텝까지 포함합니다. 적재는 PICK → PLACE입니다. 이는 동작 구간 완료이며 OpenCV를 통한 실제 부품 전달·조립 성공 판정은 아직 구현하지 않습니다.

일반 작업은 에피소드와 모든 검사가 끝나고 토크 해제 요청이 접수되면 Result `1 / IDLE`을 반환합니다. 5초 유지와 토크 OFF 확인 대기를 하지 않으며, 완료 결과는 6개 모터의 토크 OFF 확인을 의미하지 않습니다. 연결 정리가 끝나면 다음 명령을 받을 수 있습니다. 오류나 reset으로 취소된 원래 작업은 `0 / ERROR`입니다. EMER_STOP은 팔 정지·작업 보류 확인(PAUSED, 리니어 제외), RESTART는 재개 확인, RESET은 두 팔의 안전 자세 복귀 완료와 토크 해제 요청 뒤 해당 제어 Goal에 `1 / IDLE`을 반환합니다. RESET 결과 자체는 이후 자동 해제 절차의 토크 OFF 확인을 의미하지 않습니다. 접수만 되었거나 확인에 실패한 경우 성공으로 처리하지 않습니다. 실패의 상세 사유와 RESET_DONE 같은 세부 이벤트는 Pi 터미널·로그에 남깁니다. 기존 `/arm2/episode_status`, `/arm3/episode_status`는 진단용 상세 이벤트를 유지합니다.

## 배포와 기록

### 부팅 시 네트워크 준비 확인

운영 Action 서버는 `rclpy.init()` 전에 `wlan0` 링크·사용 가능한 IPv4 주소·같은 서브넷의 연결 경로를 확인한다. 같은 상태가 2초 유지돼야 DDS 통신을 초기화한다. 특정 Wi-Fi 이름이나 관제 PC의 응답을 요구하지 않으므로 관제 PC가 꺼져 있어도 Pi는 준비할 수 있다.

주소·경로 미확정 상태가 60초 지속되면 `NETWORK_TIMEOUT` 오류로 종료한다. 기존 서비스의 `Restart=on-failure`, `RestartSec=3` 정책으로 다시 시도한다. 시작 로그에는 `NETWORK_WAIT`, `NETWORK_STATUS`, `NETWORK_READY`가 남는다. 정상 기동 뒤 발생한 네트워크 단절에 대한 자동 재시작은 하지 않으며, 작업 중 재시작을 유발하지 않는다.

Pi에서 다음 명령은 네트워크 준비만 확인하고 종료한다. ROS 노드·액션 요청·모터 연결을 만들지 않는다.

```bash
source /opt/ros/jazzy/setup.bash
source /home/ubuntu/OpenCV_teach/integration/ros_ws/install/setup.bash
python3 /home/ubuntu/OpenCV_teach/integration/action_server.py --network-check-only
```

다른 인터페이스를 쓰는 배치에서는 `WORKCELL_NETWORK_INTERFACE` 또는 `--network-interface`로 변경한다. 비구동 검증용 `--check-only` 서버는 별도 ROS 도메인에서만 허용하며 이 네트워크 대기를 생략한다. `network-online.target`만 신뢰하지 않고 프로그램 시작 시 확인하므로 기존 서비스 파일에서도 다음 시작부터 적용된다.

리니어 서비스도 같은 `integration/network_ready.py`를 사용해 DDS 초기화 전에 인터페이스·IPv4·경로가 2초간 안정적인지 확인한다. `tools/linear_controller_pi5.py --network-check-only`는 ROS 노드·PWM을 열지 않고 네트워크만 검사한다. 배포된 `/home/ubuntu/project` 스크립트는 `SO101_APP_DIR`(기본 `/home/ubuntu/OpenCV_teach`)에서 공통 도우미를 읽는다. 수정은 다음 서비스 시작부터 적용되며 기존 실행 프로세스는 자동 교체되지 않는다.

- 리니어: `arm3-linear-controller.service`, `/home/ubuntu/project/linear_controller_pi5.py` + `linear_motion.py` + `linear_pwm.py`.
- 관제: `workcell-actions.service`, `/home/ubuntu/OpenCV_teach/integration/action_server.py`.
- 인터페이스: `integration/ros_ws`에서 빌드한 `host_pkg/action/Arm`.
- 설치/갱신: `sudo bash /home/ubuntu/OpenCV_teach/integration/install_services.sh`. 진행 중인 작업·최근 리니어 명령이 있으면 거절합니다.
- 에피소드: `integration/recipes.json`, Pi 각 팔의 기존 프로필·보정·에피소드 저장소 사용.
- 실행 설정: `integration/execution-settings.json` (속도 400 ticks/s, 지그 측정 4초 × 5회).
- 실행 기록: `data/episode-cli-runs/`, 마지막 상태: `data/episode-cli-arm2.json`, `data/episode-cli-arm3.json`.
- 리니어 기록: `/home/ubuntu/.local/state/arm3-linear-controller/motion.json`. 재시작 시 임의 PWM 출력이나 자동 재개를 하지 않습니다.

지그 확정 시 `A_JIG_POSE:pallet:x_mm=123.45:y_mm=-67.89:yaw_deg=12.34` 형식으로 검출 위치·각도를 기록합니다(예시 값). `x_mm`, `y_mm`는 검출 평면 좌표이며 `yaw_deg`는 검출 각도입니다. 이는 계획 입력에 사용한 확정 검출값이며 보정 후 로봇 목표 좌표가 아닙니다. 재검출로 확정되면 새 값을 기록하고, 확정 전 후보 좌표는 확정 알림으로 내보내지 않습니다. `work_watch`와 Action 서버 로그에서 확인할 수 있습니다.

## 앱에서 A/B 실행본 갱신

PC 앱은 시작 시 팔2·팔3의 Pi 에피소드와 A/B 연결, 실행 설정을 읽어옵니다. 마지막으로 읽은 Pi 원본이 바뀌지 않았다면 같은 ID의 로컬 검토 설정을 그대로 유지합니다. Pi 원본도 변경된 경우에는 로컬 수정본을 별도 사본으로 보존한 뒤 새 Pi 원본을 불러옵니다. 연결 실패 시에는 로컬 보관본임을 표시합니다. 연결하거나 로컬 저장하는 것만으로 Pi 에피소드를 덮어쓰지 않습니다.

**티칭 → 스텝 추가·편집**에서는 자세·스텝을 편집하고, **티칭 → 에피소드 조정**에서는 완료 알림과 Pi 실행 설정을 편집합니다. **Pi 에피소드 내보내기**에서 현재 Pi A/B 연결을 조회한 뒤 선택한 에피소드를 선택한 팔의 A/B 실행에 연결합니다. 전송은 기존 SSH 설정을 사용하며 모터·카메라 연결, 서비스 재시작, 실행 명령을 호출하지 않습니다.

수신 처리는 Pi의 기존 `EpisodeStore`로 로봇팔·영점·틱·티칭 기준을 검증하고 지그 모델 호환성을 확인합니다. 팔2는 `data/episodes`, 팔3은 `data/arm3-runtime/episodes`에 새 ID의 실행본을 저장한 뒤 해당 `integration/recipes.json` 항목만 원자적으로 교체합니다. 실행기와 공유하는 `data/episode-cli.lock`을 사용하여 실행 중 갱신을 거절합니다. 새 ID를 사용하므로 이미 읽은 실행본과 다른 A/B 연결은 영향을 받지 않습니다. 실행 설정 초안을 함께 전송하면 속도·지그 측정 시간·횟수·유지 시간은 선택한 팔의 A/B 작업에 공통 적용되고, 제한시간은 선택한 A/B 항목에만 적용됩니다. 설정과 연결을 함께 검증·백업하며, 연결 저장 실패 시 기존 실행 설정을 복원합니다.

조회 당시 연결·프로필·보정·실행 설정의 지문을 적용 직전에 다시 비교합니다. 파일 저장 실패 시 기존 A/B 연결을 유지하며, 같은 전송 요청의 재확인은 중복 적용하지 않습니다. 기존 연결과 이전 에피소드의 백업은 `data/episode-transfer-backups/<전송 ID>/`입니다. 통신 실패로 완료 여부가 불명확하면 앱에서 다시 조회합니다.

### 검사 실행 순서 (2026-10-23 갱신)

현재 `inspection_timing=step_complete` 에피소드는 검사 지정 스텝 자체의 완료·자세 유지를 확인한 뒤 촬영한다. 이전 형식의 다음 스텝 검사 지정은 기존 변환 규칙으로 한 번만 이동한다. 검사 스텝에서 실행 경로를 구간으로 나누고, 자세를 유지하며 서로 다른 새 프레임을 최소 관측 횟수만큼(기본 2장) 확보한다. 촬영은 최대 2초이며, 확보한 프레임을 복사해 확정한 뒤에만 다음 구간으로 이동한다. 판정은 확정한 프레임만 순서대로 처리하며 다음 이동과 병행한다. 이후 영상으로 대체하지 않고, 촬영 후 3초가 지났다는 이유로 확정 영상을 제외하지 않는다. 처리 제한시간은 프레임 확정 시점부터 저장된 `timeout_seconds`로 별도 계산한다. 확정 영상으로 판정할 수 없으면 새 위치 영상을 추가하지 않고 판정 불가로 종료한다. 촬영 중 정지·자세 변경은 해당 촬영을 실패 처리하며, 이후 동작 중 정지하더라도 이전 검사 프레임을 새로 촬영하지 않는다. 정지 확인·재개 대기 루프에서도 확정 프레임의 결과를 소비하고 다음 확정 프레임을 처리기에 전달한다. 따라서 검사 완료 뒤 사용자가 오래 정지해 있어도 대기 시간만으로 검사 실패가 되지 않는다. 재개 요청은 모든 미완료 확정 프레임의 판정이 끝날 때까지 자세 유지 상태로 대기하며, 통과한 뒤에만 재개 완료 응답과 남은 이동을 보낸다. 정지 중 새 촬영이나 새 리니어 복귀 명령은 보내지 않는다. 실제 처리기 멈춤의 제한시간은 유지하고 RESET 요청은 검사 대기보다 우선한다. 검사 기록에는 촬영 시작·각 프레임 촬영·확정·처리 시각을 남긴다. 불합격·카메라 오류·판정 시간 초과 시 즉시 팔 HOLD를 요청하고 FAILED로 종료한다. 검사 통과 전에는 연결된 단계 완료 알림과 최종 DONE을 보내지 않는다. 액션 실행 전 선택 모델의 저장 식별값과 실제 가중치를 확인한다. 팔로워 연결·보정 확인 동안 카메라·지그 모델을 예열한다. 별도 안착 검사 모델도 팔로워 연결 전에 비동기로 준비하고 한 실행의 시작 전 검사·동작 중 검사에서 직렬화하여 재사용한다. 준비용 합성 영상은 버리며 관측·검사 횟수에 포함하지 않는다. 검사별 새 프레임·취소·재시작·판정 기준은 유지하고 실행 종료 시 모델을 닫는다. 자세 유지 확인 후 리니어 이동과 첫 `safe_boundary=start` 안전 자세 이동을 병행한다(2026-10-20 사용자 간섭 없음 확인). 안전 자세 도달 후 지그를 채택하고 고정 지그 시작 조건을 검사한다. 안전 자세 이동 실패 시 지그 채택·시작 전 검사·본 작업은 진행하지 않는다. 이미 시작된 리니어는 기존 정책대로 자체 제한시간까지 진행하며, 팔 ESTOP이 리니어까지 중단하는 의미는 아니다. 리니어 위 시작 조건은 리니어 정지 후 검사하고 모든 조건 통과까지 안전 자세 이후의 작업 스텝은 대기한다. 저장된 검사 지정과 4초·5회/120초 설정은 그대로 사용한다.

### 팔로워 재연결 준비

작업 준비 시 종료된 이전 세션은 새 연결의 실패로 판단하지 않는다. `FOLLOWER_CONNECTING` 후 설정·연결을 요청하고, 새 연결의 최신 보정 일치 상태를 최대 10초 대기한다. 확인되면 `FOLLOWER_READY`를 기록하고 작업 준비를 이어간다. 새 연결 오류·시간 초과는 실패로 처리하고, 연결 준비가 끝난 이후의 연결 종료 검사는 그대로 적용한다.

### 동시 안착 검사와 알림 이름

프로토콜 4에서 도입되어 현재 프로토콜 6에도 적용되는 동시 검사는 검사 가능한 시작 조건을 한 영상에서 함께 계산하고 부품별 최소 판정 횟수(기본 2회)를 따로 누적한다. 미판정은 횟수에 포함하지 않으며 확정한 대상은 다음 계산에서 제외한다. `INSPECTION_GROUP_STARTED`와 `INSPECTION_COUNT`로 진행을 표시한다. 리니어 이동 중에는 고정 지그부터 함께 검사하고, 리니어 위 검사는 정지 후 진행한다. `work_watch`는 지그·스텝의 내부 ID를 등록 이름으로 바꾸어 보여주고 원본 이력은 유지한다.

### 조립 후 운송 연속 실행

`build_load_a` 또는 `build_load_b`는 arm2 조립을 정상 완료한 뒤 같은 제품의 arm3 운송을 이어서 실행합니다. 두 에피소드를 시작 전에 검증하고 작업 사용권을 끝까지 유지합니다. 운송 에피소드의 마지막 완제품 팔레트 안착 검사(`finished/pallet/cap_added`)가 이번 실행에서 통과하면 리니어를 조립 위치 100mm로 복귀시킵니다. 앞선 리니어 검사도 모두 통과해야 복귀를 시작하며, 팔의 남은 안전 자세 복귀와 병행합니다. 해당 안착 검사가 없으면 장치 연결 전에 거절하며, 빈 팔레트·단순 점유 검사와 이전 검사 이력은 복귀 조건으로 쓰지 않습니다.

조립 실패·reset 시 운송을 시작하지 않고, 안착 검사 실패 시 리니어 복귀를 시작하지 않습니다. estop 상태에서는 restart 전까지 새 리니어 명령을 보내지 않습니다. 이미 이동 중인 리니어는 기존 정지 규칙대로 목표까지 계속 이동합니다. ROS에서는 `/arm2/data`로 같은 명령을 보냅니다. 팔의 운송과 리니어 복귀가 모두 끝나야 `A_CHAIN_DONE` 또는 `B_CHAIN_DONE`과 성공 결과를 반환합니다. 리니어 완료는 구동 시간 기준이며 위치 실측은 아닙니다. 단독 `load_a`·`load_b`의 종료 동작은 유지합니다. 기존 터미널에는 새 셸 함수를 불러오거나 새 터미널을 열어 사용합니다.

`work_watch`의 RESET 표시는 전체 요청, 팔별 안전 복귀 시작·완료, 전체 완료로 요약합니다. 상세 진행과 중복 원문 응답은 기록에 보존하며 `work_watch --details`로 볼 수 있습니다. 오류는 기본 화면에도 표시합니다.
검사·작업 실패는 제목 아래 상세 항목을 들여써 표시합니다. 같은 실행에서 연달아 발생한 동일 검사 실패·작업 실패는 상세 원문을 한 번만 표시하고, 후속 실패에는 앞선 원인을 참조합니다. 원본 기록은 변경하지 않습니다.
기본 조회는 명령 접수, 지그 확인, 검사 결과, 주요 단계, 정지·재개와 최종 결과를 표시합니다. 개별 스텝, 검사 관측 횟수, 연결·경로 준비의 중간 알림, 지그 좌표와 정상 응답 중복은 `--details`에서 확인합니다. 리니어 완료는 구동 시간 기준이며 위치 실측이 아님을 화면에 명시합니다. 알 수 없는 새 알림·오류·거절은 숨기지 않습니다.

### 2026-10-20 리니어 하드웨어 PWM

GPIO18의 RC 신호는 RP1 PWM0 채널 2에서 50Hz로 생성한다. AI 추론과 함께 실행해도 소프트웨어 스레드가 매 펄스의 시각을 결정하지 않는다. 기존 Pi의 조립 2000μs·하차 1015μs와 10초 출력 정책은 유지한다. PWM 준비 실패 시 소프트웨어 PWM으로 대체하지 않고 서비스 시작을 거절한다. 완료 시 duty=0, enable=1로 낮은 레벨을 유지하며 위치 피드백이나 물리 도착 확인을 의미하지 않는다.

설치는 `tools/linear_controller_pi5.py`, `tools/linear_motion.py`, `tools/linear_pwm.py`, `tools/linear_pwm0.dts`, `tools/install_linear_pwm.sh`를 Pi의 같은 디렉터리에 전송한 뒤 `sudo bash <전송 디렉터리>/install_linear_pwm.sh`로 실행한다. 설치기는 에피소드 잠금·최근 리니어 이동을 확인하고 기존 코드를 `verification/linear-hardware-pwm-*`에 백업한다. 서비스의 root 소유 사전 준비 파일은 `/usr/local/lib/so101-linear/linear_pwm.py`, 설정은 `/etc/systemd/system/arm3-linear-controller.service.d/hardware-pwm.conf`이다. 매 서비스 시작에 configfs overlay로 GPIO18용 RP1 PWM0(`pwm@98000`)를 활성화하고 커널 pinctrl로 GPIO18을 연결하므로 재부팅·배선 변경이 필요 없다. 팬용 PWM1(`pwm@9c000`)을 GPIO18용으로 선택하지 않으며 팬 채널 3은 변경하지 않는다. `pwmchipN` 번호는 고정하지 않고 device-tree 주소와 호환 정보를 함께 확인한다. 준비용 overlay는 `/usr/local/lib/so101-linear/pwm0.dtbo`이며 `dtc`로 설치 시 생성한다.

### 2026-10-20 동일 프레임 AI 추론 공유

지그를 다시 검출하며 안착 상태를 검사하는 `FrameInspection`·`FrameInspections`는 같은 프레임의 AI 결과를 공유한다. 지그·부품 검사에 적용된 모델, 가중치/실행 코드 식별값, 신뢰도 기준이 모두 같을 때만 13개 클래스 추론을 한 번 수행하고 각 처리기가 필요한 마스크를 사용한다. 각 촬영 프레임마다 새 공유 객체를 만들며, 원본 픽셀 SHA-256·해상도·자료형이 다르거나 설정이 달라지면 공유 결과를 사용하지 않고 새로 추론한다. 추론 중 입력이 바뀐 결과도 버린다. 마스크는 처리기별 복사본으로 전달한다.

공유하는 것은 AI 관측뿐이다. CAD 정합·안착 범위·지그 채택 허용 오차·새 프레임 조건·연속 관측 횟수·제한시간은 기존 로직을 사용한다. 같은 프레임의 검출과 검사를 두 번의 독립 관측으로 세지 않는다. 상태 불일치가 생기면 기존 연속 관측 규칙에 따라 다시 확인하며, 불합격 조건을 충족한 결과는 계속 실패로 처리한다.

Pi 액션에서 채택된 지그 스냅샷을 사용하는 검사 단계는 지그 재검출 없이 기존처럼 부품 AI만 한 번 호출한다. 앞 단계 지그 채택에 사용한 과거 프레임을 이후 검사에 재사용하지 않는다. 카메라 안착검사 화면에서는 지그 검출이 완료된 같은 원본과 모델 설정·픽셀 해시·압축 마스크를 함께 사용한다. Pi → PC 전송은 해당 관측 영상만 무손실 PNG를 사용하고 미리보기는 기존 JPEG를 유지한다. 화면은 기존 1초 이내 영상 조건을 만족하는 완료 관측만 공유 경로로 선택한다. 오래된 관측·다른 미리보기·설정 불일치 시에는 현재 영상으로 새로 추론한다. 검사 화면을 벗어나거나 액션 검사로 전환하면 이 공유 모드를 끈다.

## 실행 흐름 분리 — 2026-10-25

공정 명령은 `episode_cli.JOB_PLANS`에서 담당 팔·제품·리니어 목표·연속 실행·PC 연산 여부를 선택한다. 저장 레시피의 스텝·검사·좌표와 완료 조건은 그대로 사용한다. `main`은 명령 해석과 분배, `run_job`은 기존 자원·잠금·실행·종료 순서를 담당한다.

## Pi 실행·복구 단계 분리 — 2026-10-25 추가 정리

`JobExecution`은 한 작업의 실행 잠금, 두 팔 연결, 리니어, 검사기와 PC 연산 연결을 관리한다. 준비·연속 단계 인계·실패·종료 정리를 나눴지만 조립→적재 사이에는 같은 잠금과 연결을 유지한다. 준비된 검사기는 적재 실행기로 한 번 인계하며 현재 단계의 실패 기록과 최종 정리 대상을 함께 갱신한다.

`PairRecovery`는 두 팔 복구의 토크 준비, 두 팔 HOLD 확인, 복귀 목표 전송/생략, 생략한 자세 재확인, 두 팔 도달 확인을 나눈다. 정지·재개와 제한시간은 이 조정 객체가 계속 관리한다. 단계의 미완료 반환은 확인된 정지·재개 후 재준비만 뜻하며 장치 오류는 예외로 전달해 HOLD 처리한다. 일반 에피소드의 `Runner.await_pause()`와 복구의 정지 처리 의미는 통합하지 않는다.

`Runner._execute()`는 검사 준비, 시작 안전 자세 확인, 검사 포함 이동, 최종 완료를 순서대로 호출한다. 기존 검사·보정 경로 계산·리니어 이동의 병행 구간은 유지한다. 완료 코드 0/130/1, 관제 상태 파이프, 정지 세대·요청 ID, 새 측정의 유효 기간, 독립 적재와 연속 공정의 리니어 복귀 차이는 변경하지 않는다.
